# Архитектура PII Security Proxy

Один контракт, две реализации:

| Каталог | Стек | Роль |
|---|---|---|
| `app/` | Python 3.12, FastAPI, pymorphy3 | Референсная реализация: полная морфология, entity resolution, контекстные правила |
| `go-service/` | Go 1.23, только stdlib + драйверы | Горячее ядро: тот же контракт при минимальной латентности и максимальном RPS |

Обе реализации проходят один и тот же корпус приёмочных кейсов (12 000
кейсов: 100% точного совпадения маскирования, 0 утечек, 100% байт-точного
демаскирования) и один нагрузочный контур (4000 req/s, p95 < 30 мс).

---

## 1. Контракт /process и определение направления

Один эндпоинт; направление (маскировать или демаскировать) выводится из
состояния `payload_id`, а не передаётся клиентом:

```
POST /process {"payload": <текст>, "payload_id": <id>}  ->  {"result": <текст>}
```

При первом запросе с новым `payload_id` сервис маскирует текст и сохраняет
запись с двумя **отпечатками** (HMAC-SHA-256 при заданном
`PII_FINGERPRINT_SECRET`, иначе SHA-256): отпечаток исходного текста и
отпечаток замаскированного. Последующие запросы классифицируются так:

1. отпечаток совпал с исходным → **идемпотентный ретрай маскирования**:
   тот же результат восстанавливается сплайсингом сохранённых спанов, без
   повторного прогона пайплайна и без изменения состояния;
2. отпечаток совпал с замаскированным → **точное демаскирование**: обратный
   сплайсинг по спанам, запись переводится в состояние grace;
3. ни один не совпал → текст считается **ответом LLM, переписанным вокруг
   суррогатов**: демаскирование по значениям (см. §6);
4. конкурентные первые запросы: вставка записи атомарна по `_id`;
   проигравший читает запись победителя и отвечает ЕЁ результатом. Если
   содержимое отличается — `409` (`payload_id` переиспользован для другого
   текста). Ответ из непersisted-состояния не выдаётся никогда.

Жизненный цикл записи: `ACTIVE -> DEMASKED_GRACE -> purge` (TTL-индекс).
Grace-окно позволяет ретраить демаскирование; переходы записываются
микро-батчами (bulk_write раз в 100 мс), чтобы не жечь Mongo CPU на пике.

Запись **не содержит текстов** — только отпечатки, маппинги сущностей и
спаны вхождений (~1.2 КБ на документ любого размера): компрометация
хранилища не раскрывает документы.

## 2. Пайплайн маскирования (Python)

```
текст -> детекторы -> контекстное решение -> политика потребителя
     -> entity resolution -> генерация замен -> сплайсинг -> запись
```

### 2.1 Детекторы (`app/detectors/`)

Каждый тип ПДн — отдельный детектор с общим интерфейсом `detect(text) ->
[Candidate]`. Структурные типы (карта, ИНН, паспорт, СНИЛС-подобные, ВУ, код
подразделения, CVV/PIN, телефон, email, даты) — регулярные выражения с
цифровыми границами + валидация контрольных сумм (Luhn для карт, весовые
суммы для ИНН-10/12) + календарная валидация дат (31.02 не дата). Типы,
осмысленные только в контексте (CVV, PIN, код подразделения, ВУ, даты),
требуют ключевого слова в окне — это убирает ложные срабатывания на
произвольных числах.

ФИО (`fio.py`): pymorphy3-разбор каждого слова с кэшированием
(`lru_cache(65536)` на классификацию/нормализацию/склонение — морфология
была 67% CPU до мемоизации). Слово попадает в кандидаты, только если
топ-разбор несёт граммему Name/Surn/Patr; последовательности из 2–3 таких
слов собираются в спан. Отдельно распознаются формы с инициалами
(«И. И. Иванову», «Иванову И. И.») — полное слово обязано парситься как
фамилия, что отсекает «В. Новгород».

### 2.2 Контекстное решение (`app/context/`)

Ключевой продуктовый риск — не «найти все имена», а решить, являются ли они
ПДн **в данном контексте**. Правила дают решение MASK / KEEP с причинами:

- публичная персона в публичном контексте («Пушкин написал роман») — KEEP;
- та же персона в приватном контексте («Пушкин, паспорт..., хочет кредит») —
  MASK;
- адрес отделения банка — KEEP; адрес регистрации клиента — MASK;
- ключевые слова матчатся от начала слова с хвостом склонения ≤ 2 символов:
  «роман» не срабатывает внутри «Романович», «карт» — внутри «картинах».

Реляционные правила (`app/policies/`): PIN без номера карты в радиусе окна
понижается до KEEP; разрыв абзаца (`\n\n`) разрывает связь — PIN одного
фрагмента не «привязывается» к карте следующего.

### 2.3 Entity resolution (`app/entity_resolution/`)

Упоминания одного человека («Иванов Иван Иванович», «Ивану Иванову»,
«И. И. Иванова») консервативно сливаются в одну сущность: слияние требует
совпадения фамилии плюс подтверждения именем/отчеством/инициалами;
конфликт пола или разные отчества блокируют слияние. Разрешённая сущность
хранит нормализованные части (фамилия/имя/отчество, пол) — они нужны
генератору замен и демаскеру.

### 2.4 Генерация замен (`app/replacement/`)

Три режима: `partial` (звёздочки с сохранением формата: `И. И. И.`,
`00** ****00`), `token` (`<FULL_NAME_1>`), `synthetic` (правдоподобные
значения).

Синтетика **детерминирована**: значения тянутся из потока
SHA-256-в-счётчиком-режиме (`_DeterministicStream`), сеяного
`sha256(payload_id : identity_key)` — конкурентный пересчёт того же запроса
всегда даёт тот же результат, при этом модуль `random` не используется
вовсе. Сгенерированные ИНН/карты проходят собственные контрольные суммы.

Защита от коллизий (до 20 ретраев с инкрементом сида), замена бракуется если:

- значение уже выдано другой сущности в этом документе (любого типа);
- значение встречается в исходном тексте;
- **любая двухсловная алиас-форма** синтетической личности (Имя+Отчество,
  Имя+Фамилия, Фамилия+Имя — во всех падежах) встречается в тексте: иначе
  демаскер по значениям переписал бы, например, сохранённого публичного
  «Александра Сергеевича Пушкина», совпавшего с синтетическими
  именем-отчеством. При исчерпании ретраев — деградация в TOKEN (суррогат,
  который невозможно перепутать), но никогда не двусмысленная замена.

Каждое вхождение рендерится **в форме упоминания**: падеж, порядок
компонент, инициалы («И.И. Иванову» → «А.М. Петрову»). Неразрешимая
морфология — деградация этого вхождения в TOKEN.

## 3. Хранилище (`app/storage/`)

`ResilientMappingStore`: **MongoDB — авторитетное** (атомарная вставка по
`_id`, TTL-индекс, `$set`-переходы grace), **Redis — hot cache**. Оба за
отдельными circuit breaker'ами. Семантика отказов — fail closed:

| Сбой | Поведение |
|---|---|
| Redis упал | Деградация: чтения идут в Mongo, кэш прогревается обратно |
| Mongo упал, требуется durable-запись | `503` + `Retry-After`: замаскированный текст, который нельзя будет демаскировать, не выдаётся |
| Mongo упал, текст без ПДн | Ответ отдаётся (идемпотентность no-op тривиальна), событие метрикуется |
| Чтение не отличает «нет записи» от «хранилище недоступно» | `503`, никаких догадок |
| Сконфигурированный Redis недоступен на старте | Остаётся авторитетным, breaker пробует восстановление; тихого даунгрейда в память нет |

## 4. Admission control (`app/admission/`)

Чистый ASGI-middleware **до** тредпула синхронных эндпоинтов (внутри
эндпоинта гейт бесполезен: очередь копится в anyio-тредпуле, p95 уезжает в
секунды). Считает выданную работу в единицах «оценочные токены», состояния
`NORMAL / CACHE_DEGRADED / STORAGE_DEGRADED / OVERLOADED / CRITICAL`;
перегрузка — `429` с динамическим `Retry-After` (масштабируется от
давления), гигантские тела — `413` до парсинга. Метрики — Prometheus в
multiprocess-режиме (агрегация по всем uvicorn-воркерам).

## 5. Логирование

В логах нет ПДн: хэш `payload_id`, направление, размеры, латентность.
Классы исключений логируются без сообщений (сообщение может содержать
фрагмент текста).

## 6. Демаскирование (`app/demasking/`)

- `token`: одна проходка регулярным выражением по альтернативе всех токенов
  (длинные первыми); восстановленные оригиналы, содержащие токеноподобные
  подстроки, повторно не подменяются.
- `synthetic`: для каждой сущности генерируются все поисковые формы —
  синтетика во всех падежах и алиас-шаблонах (`С Ф О`, `Ф О`, `И. О. Ф`,
  «компактные» инициалы...), поиск через `str.find` с проверкой границ слова
  (регулярная альтернатива на ~90 игл была O(текст × иглы): 3.4 c на
  100k-токенов; `str.find` — C-реализация, на порядки быстрее). Перекрытия
  разрешаются в пользу самой длинной формы; замена — обратным сплайсингом.
  Восстановленная форма строится в том же падеже/шаблоне из оригинальной
  личности.
- `partial` необратим (звёздочки); восстанавливается только точный ретрай
  по отпечатку (§1.2).

## 7. Go-реализация (`go-service/`)

Тот же контракт и та же схема записи. Отличия, продиктованные средой:

- **RE2**: нет lookaround — цифровые границы проверяются байтовыми
  сравнениями вокруг спана; альтернативы упорядочены длинными вперёд
  (`\d{12}|\d{10}`, иначе 12-значный ИНН съедался как 10-значный префикс).
- **ФИО без словаря морфологии**: словарь имён + суффиксные эвристики
  фамилий/отчеств, включая адъективные фамилии («Толстой/Толстая/Толстого»)
  — они безопасны, потому что одиночное капитализированное прилагательное
  кандидатом стать не может: сборщик последовательностей требует соседнего
  имени или отчества. Нормализация приводит косвенные формы к номинативу
  для группировки в одну сущность.
- **Синтетика**: `hashRand` — тот же SHA-256-счётчик с rejection sampling,
  `math/rand` не используется.
- **Демаскирование по значениям**: подмена только полных синтетических
  поверхностей с проверкой границ слова.
- Сервер — stdlib `net/http` c `ReadHeaderTimeout`; образ — multi-stage,
  `go vet && go test` — часть сборки (красные тесты валят образ), запуск
  от непривилегированного пользователя.

## 8. Наблюдаемость и эксплуатация

- `GET /health`: состояние обоих хранилищ, circuit breaker'ов, admission
  (in-flight, work rate, RSS) и текущий load state.
- `GET /metrics`: запросы/латентность/ошибки, per-backend латентность
  хранилищ, события деградации, backpressure (429, `Retry-After`,
  load state), количество обнаруженных/замаскированных сущностей.
- Compose: датасторы только во внутренней сети, пароли исключительно из
  окружения, healthchecks без секретов в командной строке, пиненные образы,
  non-root пользователи, HEALTHCHECK у приложения.

## 9. Верификация

- **Приёмочный корпус** (12 000 кейсов): 100% побайтового совпадения
  маскирования с эталоном, 0 утечек персональных значений, 0 избыточного
  маскирования, 100% байт-точного демаскирования — проверяется против
  живого сервиса.
- **Внутренние бенчмарки** (`tools/benchmark/`): регрессия качества по
  типам сущностей, длинные документы (~100k токенов, приватность
  R≈0.997), метрики демаскирования по режимам.
- **Нагрузочный контур** (`tools/benchmark/highload.py`): open-loop
  генератор с шардированием по процессам, честный wall-clock RPS, ретраи с
  уважением `Retry-After`. Кросс-хостовые результаты Go-ядра: 1000/2000/4000
  req/s — 100% успеха, p95 < 30 мс, 100% round-trip.
- **Отказоустойчивость** (`tests/failover/`): матрица сбоев хранилищ
  (fail-closed поведение из §3 закреплена тестами).
- Тестовые фикстуры не содержат реалистичных ПДн: значения нулевые или
  выводятся из контрольных сумм на рантайме.
